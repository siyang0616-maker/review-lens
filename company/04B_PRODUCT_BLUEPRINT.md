# Product Blueprint

## Purpose

This document defines exactly what the MVP product must become before the Master PRD is written.

This is not a coding sprint.
This is not a UI redesign sprint.
This is not a feature expansion sprint.

Review-to-Revenue AI is a Revenue Action Platform for Customer Voice.

It must help the user know:

1. Who to contact.
2. What to send.
3. What to publish.
4. What script to improve.
5. What happened after action.

## 1. MVP Product Definition

The MVP is:

```text
Customer voice input
-> Revenue action board
-> Follow-up / content / script recommendations
-> Outcome tracking
-> Report export
```

The MVP is not a review analyzer, CRM, or generic AI report tool.

The MVP must turn messy customer language into a weekly set of revenue actions.

Core MVP definition:

> Review-to-Revenue AI takes customer conversations, identifies revenue signals, creates a prioritized action board, helps the user execute follow-up/content/script work, tracks what happened, and exports a Review-to-Revenue Action Report.

The MVP must be usable without integrations.

The MVP must work with pasted text and CSV-style input.

The MVP must make value clear within 30 seconds through demo data or user-provided customer voice.

## 2. Core User Workflow

The product should support a simple weekly operating rhythm.

### Monday: Review This Week's Revenue Actions

User job:

- Open the dashboard.
- Load demo data or paste current customer voice data.
- Review Leads to Rescue, Actions Ready, Revenue at Risk, and Today's Priority Actions.

Product answer:

- Who should I contact first?
- What is blocking revenue this week?
- Which actions matter most?

### Tuesday: Send Follow-up Messages

User job:

- Open the follow-up message library.
- Copy messages for cold, hesitant, or comparison-stage leads.
- Mark actions as copied or sent.

Product answer:

- What should I send?
- Why should this message work?
- Which objection does this message address?

### Wednesday: Publish Objection-based Content

User job:

- Review content ideas.
- Choose one objection-based content topic.
- Publish or draft content that answers a repeated customer concern.

Product answer:

- What should I publish?
- Which objection does it remove?
- Why is this content useful now?

### Thursday: Improve Sales Scripts

User job:

- Review script suggestions.
- Replace vague script lines with clearer, evidence-backed lines.
- Prepare for the next consultation, call, or sales conversation.

Product answer:

- What script should I improve?
- Which trust barrier does it handle?
- What stronger line should I use?

### Friday: Track Outcomes

User job:

- Mark actions as replied, booked, won, lost, or ignored.
- Review what worked.
- Export or save the weekly action report.

Product answer:

- What happened after I acted?
- Which actions created replies, bookings, or wins?
- What should improve next week?

## 4. Revenue Action Board

The Revenue Action Board is the product's core screen.

It is where the product stops being a report and becomes a weekly operating tool.

The user must understand what to do next within 30 seconds.

The board must show:

- Leads to Rescue.
- Actions Ready.
- Revenue at Risk.
- Today's Priority Actions.
- Follow-up message preview.
- Content to publish.
- Script to improve.
- Outcome status.

Primary board promise:

> Open the board and know which revenue action to take next.

Board hierarchy:

1. Metrics that show urgency.
2. Priority actions that show what to do.
3. Evidence that shows why the action matters.
4. Execution controls that help the user copy, send, publish, improve, or mark status.
5. Outcome status that closes the loop.

The board should avoid:

- Dense charts.
- Sentiment dashboards.
- Review-topic visualizations.
- CRM stages.
- Generic AI summaries.

The board should prefer:

- Action title.
- Target segment.
- Why now.
- Evidence.
- Recommended action.
- Suggested message.
- Expected outcome.
- Priority.
- Status.

## 5. RevenueAction Model

Canonical model:

```ts
type RevenueAction = {
  id: string;
  type: "follow_up" | "content" | "script" | "competitor_gap" | "trust_asset";
  title: string;
  targetSegment: string;
  whyNow: string;
  evidence: string[];
  recommendedAction: string;
  suggestedMessage?: string;
  expectedOutcome: string;
  priority: "low" | "medium" | "high";
  status: "ready" | "copied" | "sent" | "replied" | "booked" | "won" | "lost" | "ignored";
  createdAt: string;
  updatedAt?: string;
};
```

Model principles:

- `RevenueAction` is the primary executable entity.
- Every action should be tied to customer evidence.
- Every action should have an expected business outcome.
- Status should support outcome tracking without becoming a CRM.
- Actions should be understandable without reading the full report.

Action types:

- `follow_up`: rescue or restart a conversation.
- `content`: publish content that handles a repeated objection.
- `script`: improve consultation or sales language.
- `competitor_gap`: use competitor weakness as positioning.
- `trust_asset`: create proof that reduces trust barriers.

## 7. First Beachhead Product Mode

First real validation mode:

> Franchise / Business Consulting.

This mode should be designed for founder-led consultants who handle high-ticket franchise, business opportunity, or self-employment advisory leads.

### Data The Founder Can Use

Usable data:

- Lead CSVs.
- Consultation notes.
- KakaoTalk / SMS / DM snippets.
- Form submissions.
- Blog inquiries.
- Sales notes.
- Competitor complaints.
- Repeated customer questions.
- Content comments.

Why this data works:

- It contains buying hesitation.
- It contains repeated objections.
- It contains decision-stage language.
- It is close to revenue action.
- It does not require integrations for early validation.

### Objections That Appear

Common objections:

- Initial investment amount.
- Monthly profit.
- Payback period.
- Failure risk.
- Brand comparison.
- Location quality.
- Operator workload.
- Spouse or family approval.
- Trust in consultant.
- Proof of actual outcomes.
- Difference between advertised and real cost.

### Follow-up Actions That Matter

Follow-up actions:

- Send payback-period explanation.
- Send investment-risk breakdown.
- Send family approval summary.
- Send brand comparison checklist.
- Send location-risk explanation.
- Send realistic operator workload guide.
- Send proof asset or case example.
- Restart no-response leads with a specific decision aid.

### Content Ideas That Matter

Content ideas:

- "Why payback period varies by brand and location."
- "What to ask before comparing franchise brands."
- "How much cash buffer should a first-time operator keep?"
- "The hidden reason leads stop after asking about monthly profit."
- "How to explain franchise risk to your spouse or family."
- "Why low initial investment does not always mean safer."

### Sales Scripts That Matter

Script improvements:

- Replace vague reassurance with quantified risk framing.
- Replace "good brand" language with comparison criteria.
- Replace "it depends" with decision conditions.
- Replace generic follow-up with objection-specific next step.
- Replace confidence claims with evidence and scenario ranges.

### Why This Is The Fastest PMF Path

Franchise / Business Consulting is the fastest PMF path because:

- Founder domain knowledge is strongest.
- Customer language is already known.
- Objections are repeated and high-value.
- Manual delivery can validate the workflow quickly.
- One recovered conversation can justify paid report pricing.
- The first vertical playbook can be created before building heavy software.

## 10. Outcome Tracking

Outcome tracking is critical because it starts the data flywheel.

Without outcome tracking, the product is only a better recommendation tool.

With outcome tracking, the product becomes a Revenue Intelligence Layer for Customer Voice.

Track statuses:

- copied
- sent
- replied
- booked
- won
- lost
- ignored

Why this matters:

- `copied` shows message usefulness.
- `sent` shows action execution.
- `replied` shows conversation recovery.
- `booked` shows consultation or booking movement.
- `won` shows deal impact.
- `lost` shows failed action or poor fit.
- `ignored` shows weak message, low urgency, or wrong timing.

Outcome tracking creates:

- Proof of recovered value.
- Better weekly recommendations.
- Stronger vertical playbooks.
- A reason to subscribe.
- A defensible data flywheel.

Outcome tracking non-goals:

- No guaranteed attribution.
- No financial forecasting.
- No multi-touch analytics.
- No automated CRM sync yet.

## 13. Product Success Criteria

The MVP succeeds if:

- User loads demo data and understands value in 30 seconds.
- User wants to try their own data.
- User copies at least one follow-up message.
- User sees a clear report worth paying for.
- User understands this is not a review summarizer.

Behavioral success signals:

- User asks, "Can I paste my own notes?"
- User asks, "Can I use this for my leads?"
- User copies a message without being prompted.
- User identifies a real lead they should contact.
- User says the report is useful enough to send, sell, or review with a team.
- User marks at least one action outcome.

Commercial success signals:

- User accepts a free diagnostic.
- User pays for a one-time Revenue Action Report.
- User asks for setup help.
- User asks how to use this weekly.
- User sees the tool as a revenue action layer, not a report generator.

Failure signals:

- User only reads the output and takes no action.
- User says it is just a review summary.
- User cannot identify a lead, message, content idea, or script change.
- User does not want to paste their own data.
- User sees no report value.

## 15. Product Risks

### Risk 1: Product still looks like a review analyzer.

Mitigation:

- Lead with revenue action board.
- Use customer conversations language.
- Show follow-up, content, script, and outcome surfaces clearly.

### Risk 2: Product looks like a dashboard.

Mitigation:

- Prioritize action cards over charts.
- Keep the first screen focused on what to do next.
- Make copying, sending, publishing, improving, and tracking visible.

### Risk 3: Product looks like a generic AI report tool.

Mitigation:

- Every report section must map to action.
- Every recommendation should include evidence and expected outcome.
- Keep outcome tracking connected to report export.

### Risk 4: Product tries to serve too many verticals too soon.

Mitigation:

- Make Franchise / Business Consulting the first real validation mode.
- Keep other verticals as demos until paid demand proves expansion.

### Risk 5: Outcome tracking is ignored.

Mitigation:

- Make outcome status lightweight.
- Tie Friday workflow to outcome tracking.
- Use outcome summary in the report.

### Risk 6: Users do not provide enough useful data.

Mitigation:

- Provide clear input examples.
- Use demo modes to teach what good input looks like.
- Offer setup service for data cleanup.

### Risk 7: Revenue language creates unrealistic expectations.

Mitigation:

- Use estimated revenue at risk.
- Avoid guaranteed revenue claims.
- Frame the promise around better action and recovered conversations.
